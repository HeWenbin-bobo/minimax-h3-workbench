# 自写探针全绿，官方 E2E 却抓到了 bug：探针的覆盖盲区

**记录时间**：2026-10-21 探索期。这条是"我的验证方式本身失效"的实例，比任何单个 bug 都值得记。

## 发生了什么

我在一次重构里把普通对话分支写成了：

```ts
void runPlainChat()
  .catch(async (error) => { ... })       // 失败有收尾
  .finally(() => { ... });               // 异常有收尾
// ← 漏了 .then(() => done({ ok: true }))
```

**成功路径上什么都不发**。后果：渲染端收不到 `llm:done` → 不清 `generatingIds` →
会话**永久卡在「生成中」**（停止键一直在、再也发不出新消息）。这是最常走的路径。

期间我跑过三个自写探针，**全部通过**：

| 探针 | 它验了什么 | 为什么没抓到 |
|---|---|---|
| `probe-real-overflow-recovery` | 超窗后能否当轮恢复 | 只断言"正文有没有到"，不断言"有没有收尾" |
| `probe-long-session-perf` | 300 条历史下的流式性能 | 只比长度与耗时，从不检查是否退出生成态 |
| `probe-user-journey` | 真人流程走一遍 | **从没关掉「智能体」**——走的是智能体路径，那条路有独立收尾逻辑，把这个 bug 完整遮住了 |

抓到它的是仓库自带的 `.e2e/test-08-playground-concurrency.mjs`（16/16 → 14/16）。

## 两个可复用的教训

### ① 有两条路径的功能，两条都要覆盖

这个应用里「普通对话」与「智能体」是两套完全独立的收尾逻辑，
而游乐场**默认开启智能体**。任何"只跑一遍流程"的探针，默认走的是智能体路径。

**规矩**：探针里凡是涉及"一轮对话怎么结束"的断言，都要**显式关掉智能体再跑一遍**，
并在断言里带上"确认已关闭"这一条前置
（`probe-user-journey` 现在有第 ⓪ 条就是这个作用）。

### ② 断言"内容到了" ≠ 断言"这一轮结束了"

合法的收尾至少包含三件事，探针应分别断言：

- 正文完整（`fullText` 或气泡文本）
- **`done` 事件到了**（`generatingIds` 被清、气泡 `streaming: false`）
- 界面退出生成态（停止键消失、发送按钮可用）

我之前的探针大多只验第一条。这次补上第 ⓪ 条之后，journey 探针的"本轮耗时"
从 321ms 变成 1310ms——路径真的不一样了，这个数字本身就是"覆盖到了"的证据。

### ③ 变异验证是探针的"体检"，不做就等于没测

本轮做连点守卫时，先写的判据是「上游请求次数 `<= 2`」（想给"服务商不支持模型列表、
回退发一条对话"留余量）。跑起来 9/9 全绿，看起来没问题。
**但把守卫代码删掉重新 build 再跑，仍然 9/9** —— 连点发出的 3 次请求里只测到 2 次，
被那条余量吞掉了。

改成严格 `=== 1` 后，删守卫立刻变红（2 次）、恢复守卫变绿（1 次）。

**规矩**：每写一条"某操作只发生 N 次 / 不发生"的断言，都要手动把被测逻辑破坏一次，
确认断言真的会红。判据里的每一分余量，都可能是缺陷的藏身处。

### ④ 切页类探针：离开时长必须跨过整轮时长

测「生成中切页」时，第一版是"流式 6 秒、中途切走 4 秒"。这个设计**测不到补齐通道**：
切回时 `llm:done` 还没发生，它会正常送达并自带 `fullText`，正文自然完整。
于是无论补齐通道好坏，断言都通过——变异验证也全绿，是一条彻底的假通过。

改成"流 4.2 秒、切走 7 秒"（离开时长 > 整轮时长），`llm:done` 必然发生在组件卸载期间、
被丢弃，此时只有主进程保存的 `turnState` 能补齐。这才测到了目标通道：
把主进程两处 `turnState.fullText = turnText` 去掉后，气泡停在「段0 段1」、
缺段 `[2,3,4,5,6]`（正是切页前已渲染的部分）。

**规矩**：测"离开期间发生了什么"时，先算清楚"要离开多久才能让那件事真的发生在离开期间"，
并把这段时长写进注释——否则下一个人调快测试时会不知不觉把覆盖调没。

### ⑤ 只在多轮之后才暴露的状态，单轮测不出来

`llm:turn-state` 是**读一次就删**（避免下一轮读到上一轮的 `done=true`）。
单轮切页永远通过；清错对象 / 清得太早这类错误，要到**第二轮**才表现出来。
本轮套件因此扩成连续三轮，并在变异（无条件 `delete`）下如期掉到 5/9：
第 2 轮缺段、第 3 轮反而通过（那时 map 里已无残留）。

**规矩**：凡是"读后即删 / 消费一次"的状态，测试至少跑两轮，并显式断言第二轮仍然正常。

## 怎么快速定位"是不是我引入的"

用 `git worktree` 在会话起点建一个基线目录，把 `node_modules` 用 junction 链过去
（Windows：`cmd //c "mklink /J <worktree>\\node_modules <repo>\\node_modules"`），
在基线里 `npm run build` 后跑同一套 E2E：

- 基线通过、当前失败 → **本轮引入的回归**，去 `git log --oneline <base>..HEAD -- <相关文件>` 找嫌疑；
- 两边都失败 → 不是本轮引入的，另开一条线排查。

本次靠这一步确认了"确实是本轮引入"，避免把时间花在排查历史遗留问题上。

## 排除嫌疑的顺序

先排除**改动最少、最容易推翻**的：

1. 把可疑新增逐个注释掉跑一遍（本次先试了 `stop()` 里的缓冲清理、再试计划恢复，两次都仍失败）；
2. 再往上游找（本次找到主进程的 `runPlainChat` 链）。

注释掉再跑比"读代码猜"快得多，而且结论是确定的。
